Methodology

Human-directed AI-assisted development

AI tools write a lot of code quickly. Whether that code works, is honest about its limits and can be maintained depends on the person directing the tools. This page describes how that direction works here.

What this is not. The method is written in the public repository AI Coordinator Portfolio, which contains playbooks, role definitions, prompt templates and decision records. It contains no agent runtime, scheduler or orchestration service, and it does not run anything by itself. It is a method, not a platform or a product.

  1. A person owns the objective

    Guilherme sets the goal, the constraints and the approval gates, and gives final acceptance. Escalations and decisions go to him.

  2. The problem becomes checkable criteria

    Each cycle starts with a briefing: problem, audience, constraints, what already exists and an observable definition of success. It produces 5 to 10 pass/fail acceptance criteria, with scope in and out written down.

  3. Work is assigned by role

    Product, Code, QA, Docs and Commercial are roles. Each one can be filled by a person, by an AI tool under supervision, or by both, and each role has a minimum artifact to hand over.

  4. Every handoff is written

    A handoff records what was delivered, what is pending, which criteria to validate now, how to verify them (commands and steps), and the blockers.

  5. Results are inspected, and rejected when needed

    QA sends reproducible bugs back. Work outside the criteria is not accepted. When something is ambiguous (two versions of a project, missing source, a branch conflict), work on that item stops and the question is reported rather than guessed.

  6. Only executed checks count

    "Report only checks actually performed and results actually observed." A test counts as passing only after it has run, and the command goes in the log. This site follows the same rule: every number on it points to a test log, a CI record or a cited repository document.

  7. Irreversible actions wait for the owner

    Deleting branches or releases, changing visibility or licences, rewriting history and touching secrets all need explicit approval from the owner.

Applied example

GitHub & Project Estate Consolidation: a self-directed audit and consolidation of Guilherme's own GitHub account and workspace. AI coding agents did the inventory, comparisons, scans, edits and report drafting; Guilherme made every decision on visibility, licensing, branding and ambiguous projects. A secret scan over the history of 41 repositories returned 0 findings. A merge that conflicted with newer work from a parallel agent session was aborted rather than forced. Not paid client work.

→ github.com/lughlammas/ai-coordinator-portfolio/blob/main/case-studies/github-project-estate-consolidation.md

What we do not claim

No productivity, speed or quality figures are claimed for this method. It defines a process; it does not prove by itself that any product passed QA.
