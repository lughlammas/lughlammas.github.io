01Problem

Requests arrive through forms and inboxes. Someone reads each one, decides what it is and how urgent it is, writes a reply and keeps track of it. Most of that is routine, but the reply still needs a person's judgement.

02Context

FLOWDESK is ARBOCK LABS' demonstration for S01 · Business Automation & AI. It uses synthetic data only, sends no email, and has not been deployed: there is no Cloudflare account yet.

03Solution

Form → Triage → Reply suggestion → Human approval → Record. - A private sandbox for each visitor. The first visit issues an anonymous session cookie (HttpOnly, Secure, SameSite=Lax) and opens a sandbox loaded with a synthetic seed of six tickets. A visitor cannot see or change another visitor's tickets. After 24 hours the sandbox is replaced by a fresh seeded one. - Intake form. Each invalid field gets its own error message, linked to the field (aria-invalid, aria-describedby). - Rule-based triage sets a category and a priority, and records the reasons. A person can override the classification, and the override is logged. - Editable reply suggestion. It is labelled "Simulação (regras) — não é um modelo de IA" in the interface and in the API, and the API marks the provider as is_ai_model: false. - Human approval is mandatory. A ticket cannot be approved before a suggestion exists, and rejecting it requires a reason, typed in an inline field. No email is ever sent. - Event history with the author of every state change, edit, override and webhook attempt. - Signed webhooks (HMAC-SHA256) on every state change, retried with backoff for up to three attempts, each attempt recorded in the ticket's history. - Token-protected admin. The admin routes require a bearer token, and anything else is refused with 401. In production mode, the server refuses to serve at all unless that token is configured. - Error and empty states in the API and in the interface.

04Architecture

A Cloudflare Worker serving a static interface and a REST API, with a D1 (SQLite) database. Data is isolated per visitor sandbox. Locally it runs on wrangler dev --local (miniflare/workerd). Suggestions come from a pluggable provider interface. The only provider today is the rules simulation, so connecting a real model later would mean adding a provider, which needs an authorised provider.

05Evidence

Everything below ran locally on 2026-10-19, against code identical to the cited commit: - Unit and integration tests passed. They cover sandbox isolation, the session cookie, 24-hour expiry, admin authentication, production refusal, rate limits and webhook retry. - Browser end-to-end checks passed. They cover: - the simulation label; - per-field error messages; - an XSS payload rendered as plain text; - the full triage → suggestion → edit → approve → register flow, and reject with a reason; - the event history; - the empty state; - no horizontal overflow at 360, 390, 768 and 1280 px; - a second visitor seeing only their own seed tickets; - no console errors. - API demo with curl. - The sandbox cookie lasts 24 hours. - Visitor B gets 404 on visitor A's ticket. - The admin route returns 401 without the token, with a wrong token or with a visitor cookie, and 200 with the token. - Production mode without the token answers 503 on every route. - A forged webhook signature returns 401. - An external webhook receiver verified every signed event it received. - Security checks: - static checks; - gitleaks and trufflehog, both run locally, with no findings; - npm audit with no vulnerabilities.

Counts from the local run of 2026-10-19 at commit b9e77fb, reproduced independently by QA: 94/94 unit and integration tests, 64/64 browser checks, 5/5 webhook signatures verified by an external receiver.

06Human role and AI tools

Human approval is a step inside the product: nothing is approved or registered without a person acting, and every action is logged with its author. The software was built through human-directed AI-assisted development.

08Limitations

  • Suggestions are rule-based: a simulation, not an AI model.
  • No hosting. It is a local demo with hosting pending: there is no Cloudflare account and nothing is deployed, so behaviour at the edge has not been observed.
  • No remote CI. A workflow file exists, but the repository has no remote, so it has never run.
  • Webhook retry is not durable. Retries run in the same request lifecycle. Without Cloudflare Queues, pending attempts can be lost if the worker is stopped.
  • No scheduled sandbox cleanup. Expired sandboxes are removed only when accessed or through the admin route; there is no scheduled job.
  • Accessibility was checked only automatically (axe-core, pa11y) on a local server, with no screen-reader test.
  • Visitors are anonymous and the admin uses a single shared token; there are no user accounts.
  • The rate limit is a simple fixed window, not abuse-grade.
  • The interface is in English, apart from the Portuguese simulation label.

09Commercial relevance

It shows the shape of an automation in which software does the sorting and drafting, a person keeps the decision, and every step leaves a record. That is the core of S01.
